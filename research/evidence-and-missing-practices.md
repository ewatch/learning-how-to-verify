# Evidence Base and Missing Practices

Research for the "inverted funnel" verification site (codebase → static analysis → verification → prose → human review).
Practice list based on Cindy Sridharan's testing-in-production diagram, plus our own additions.
Compiled 2026-11-16.

## How to read this

**Evidence strength**
- **strong**: replicated, large-scale or controlled studies that point the same way. Can include large industrial deployments with measured outcomes.
- **moderate**: one solid peer-reviewed study, or several industrial reports, or correlational survey data at scale (e.g. DORA).
- **weak**: anecdotal, experience reports without measured outcomes, small samples, or preprints only.
- **none found**: no empirical study of the practice's *effect* found in this research pass. The practice may still be sensible; nobody has measured it.

**Verification marker** (honesty about sourcing)
- **[V]**: citation and finding checked by web search or fetch during this research session.
- **[K]**: a well-established, widely cited paper given from prior knowledge, with venue and DOI. It was not re-fetched in this session, so spot-check it before publishing.

"AI" columns cover evidence specifically about LLMs or coding agents. Most AI-specific work is 2023–2026 and much of it is arXiv preprints. Treat it as weaker than its venue-equivalent SE evidence unless noted.

## A) Missing practices: proposals

The lists already cover a lot. These are the widely recognised practices that are missing and matter for AI-written code. The list is curated, not exhaustive.

| # | Practice | One-line definition | Funnel layer | Lifecycle phase | Why it matters for AI-written code | Recommendation |
|---|---|---|---|---|---|---|
| 1 | **End-to-end (E2E) tests** | Drive the whole system through its real UI or API like a user would. | Static analysis / tests (top of test pyramid) | Pre-production / Deploy | Agents can make unit tests pass while the assembled system is broken. E2E is the check that the pieces actually connect. | **Include**. Sridharan's list has acceptance and integration but no E2E; it is the most commonly named test type that is missing. |
| 2 | **Snapshot / approval / golden-master / characterization tests** | Record current output and fail when it changes; for legacy code, pin existing behaviour before refactoring. | Tests | Pre-production | Lets you refactor or let an agent rewrite code with a "behaviour did not change" guard. Risk: agents (and humans) blindly re-approve snapshots. | **Include as one entry** (merge snapshot + approval + golden master + characterization). |
| 3 | **Visual regression testing** | Pixel or DOM diffs of rendered UI against a baseline. | Tests | Pre-production | Agents cannot see the UI they change unless given screenshots. Visual diffs catch layout breakage that unit tests miss. | **Merge into UI/UX tests** (or into #2 as "visual snapshot"). |
| 4 | **Metamorphic testing** | Check relations between outputs of related inputs (e.g. `sort(reverse(x)) == sort(x)`) when there is no exact oracle. | Tests | Pre-production | Solves the oracle problem: you do not need to know the right answer, only how answers relate. Useful when an agent wrote both code and expected values. | **Merge into property-based testing** (as "properties without an oracle"). |
| 5 | **Design by contract / assertions** | Pre-/postconditions and invariants checked at runtime (or statically). | Verification (runtime) / codebase | Pre-production + Post-release | Contracts turn the spec into executable checks that the agent's code must respect, and they fail loudly near the bug. | **Include**. Bridges "codebase" and "formal verification" (Dafny/Verus specs are contracts). |
| 6 | **Runtime verification** | Monitor executions or logs against a formal spec (e.g. AWS PObserve checking logs against P specs). | Verification (runtime) | Release / Post-release | Catches spec violations in real traffic that tests never exercised. | **Merge with #5** under "contracts and runtime verification", or keep separate if the site has a "runtime" verification page. |
| 7 | **Sanitizers (ASan, UBSan, TSan, MSan)** | Compiler instrumentation that detects memory errors, undefined behaviour and data races at runtime. | Verification (runtime) | Pre-production (tests, fuzzing) | LLMs produce memory-unsafe C/C++ at notable rates. Sanitizers make fuzzing and tests actually *see* those bugs. | **Include**, or merge into fuzzing ("fuzzing + sanitizers" is the standard pairing). |
| 8 | **Symbolic execution / bounded model checking** | Explore program paths with symbolic inputs (KLEE, SAGE) or exhaustively check all executions up to a bound (CBMC, Kani). | Verification (formal) | Pre-production | Push-button formal tools that need far less proof effort than Dafny/Lean. A realistic middle ground for agent-written systems code. | **Merge into formal verification** as the "automated end" of the spectrum. |
| 9 | **Model-based testing** | Generate tests from a model (state machine) of intended behaviour. | Tests / verification | Pre-production | The model is a compact spec humans can review instead of reviewing thousands of generated tests. | **Skip or merge into property-based testing** (stateful PBT is the modern form). |
| 10 | **SAST / DAST / SCA (dependency scanning)** | Static security analysis of source; dynamic scanning of a running app; scanning third-party dependencies for known CVEs. | Static analysis (SAST, SCA); runtime (DAST) | Pre-production / Deploy | AI code has measurable vulnerability rates (≈40% in security-relevant Copilot scenarios), and agents add dependencies freely. | **Include as one "security scanning" entry**; mention SAST as a feedback loop for agents. |
| 11 | **Secret scanning** | Detect credentials committed to code or history (pre-commit and server side). | Static analysis | Pre-production (pre-commit, CI) | LLMs can reproduce memorised credentials, and agents hard-code keys. One study found hard-coded credentials dominate critical security smells in agent PRs. | **Include**, or merge into #10. Cheap, high-value, very early in the funnel. |
| 12 | **Supply-chain integrity (SBOM, SLSA, provenance, pinning)** | Know and attest what went into a build; verify artefact provenance. | Static analysis / CI | Deploy | Agents install packages, including hallucinated package names ("slopsquatting"). Provenance and lockfiles limit the damage. | **Merge into #10** as "dependencies and supply chain". Little effect evidence. |
| 13 | **Accessibility testing** | Automated (axe, Lighthouse) and manual checks against WCAG. | Tests | Pre-production | Agents produce plausible-looking UI that often ignores semantics and ARIA. Automated checks are cheap. | **Merge into UI/UX / usability**. |
| 14 | **Flaky-test management / test hygiene** | Detect, quarantine and fix non-deterministic tests. | Tests / CI | Pre-production | Agents treat a red test as a signal. A flaky test teaches the agent (and humans) to ignore red, or to "fix" the test. | **Include as a sidebar on CI**, not its own practice. |
| 15 | **Evals (task-level evaluation suites)** | Repeatable suites that measure an agent's or model's success on representative tasks (SWE-bench style). | Verification of the *process* (meta-layer) | Pre-production (of the agent setup) | You verify the agent configuration (model, prompts, AGENTS.md, tools) the way you verify code. Changes to rules files should be evaluated, not assumed helpful. | **Include**. Fits best next to "prose" because it is how you test prose. |
| 16 | **LLM-as-judge / AI code review** | An LLM grades or reviews outputs (patches, PRs) against a rubric. | Human review layer (automated pre-review) | Pre-production | Scales review, but agreement with humans depends strongly on rubric. Precision of AI review comments is modest. | **Merge into code review** as "automated first pass". Not a replacement. |
| 17 | **Test generation by agents (coverage- or mutation-guided)** | The agent writes tests, filtered by build, pass, coverage gain or killed mutants. | Tests | Pre-production | Industrial results (Meta) are good *when filtered by mechanical checks*; unfiltered self-written tests risk "self-deception". | **Merge into mutation testing + unit tests** as the AI-era use of them. |
| 18 | **TDD as agent loop / spec-driven development** | Write (or approve) tests or specs first; the agent iterates until they pass. | Prose + tests | Pre-production | Gives the agent an external oracle that a human approved. The strongest AI-specific evidence of any practice here is for test feedback. | **Include** (combine TDD-as-agent-loop and spec-driven development). Spec-driven by itself has no effect evidence yet. |
| 19 | **Test-tamper protection (read-only tests, hidden holdout tests)** | Stop the agent from editing or special-casing the tests it is judged by. | CI / process | Pre-production | Frontier agents modify or game tests on impossible tasks; read-only or hidden tests reduce this. | **Include**, AI-specific and well evidenced (ImpossibleBench). Can live inside #18. |
| 20 | **Sandboxing / least-privilege agent execution** | Run agents in containers/VMs with limited network, credentials and filesystem access. | Outside the funnel (blast-radius control) | All phases | Limits damage from wrong or prompt-injected agent actions; also makes running tests safe. | **Include as a short "guardrails" note**; it is containment, not verification. No effect studies found. |

**Skipped on purpose:** code metrics/complexity thresholds (fold into lint), pair programming (fold into code review), formal code inspection (Fagan; fold into code review), game days (fold into chaos testing), and SRE error budgets (fold into monitoring/release).

### B5. Prose layer (rules, skills, AGENTS.md)

| Practice | General SE evidence | Strength | AI/LLM-specific evidence | Strength |
|---|---|---|---|---|
| AGENTS.md / rules files / skills | Not applicable (agent-specific). ## Summary of gaps

1. **Most "production" practices lack effect evidence.** Canarying, feature flags, chaos, shadowing, soak/load tests, RUM, on-call: experience reports and correlational surveys only. No AI-specific studies at all.
2. **Prose (AGENTS.md, skills) is the least-evidenced layer**, and the best study (Gloaguen et al. 2026) is negative for correctness. Treat prose as something to evaluate, not assume.
3. **Tests are necessary but insufficient for agents.** Three independent lines of evidence: PatchDiff (29.6% behaviourally divergent "passing" patches), METR (~half of passing PRs not mergeable) and ImpossibleBench (agents game tests). This supports the funnel ending in human review, plus differential, mutation and property testing as stronger oracles.
4. **Formal verification with LLMs is promising but benchmark-level.** DafnyBench/Verus-Bench tasks are small; no industrial report of LLM-written proofs at scale found.
5. **Codebase quality → agent success is unmeasured.** It is a central claim of the funnel ("good API design and architecture"), but no study measures it directly.
